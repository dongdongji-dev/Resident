# Skill 开发规范（Resident 通用参考文档）
---

## 1. 目录结构

```
.skills/<name>/
  SKILL.md              # ★ 触发说明：什么时候该用它（系统提示词只扫这一个文件）
  README.md             # 给人看的：这是什么、怎么起、怎么调、有哪些动作
  start.sh              # ★ 只有常驻服务才需要：start | stop | status | --clean（幂等）
  requirements.txt      # 依赖（有代码就有这个文件；无第三方依赖写注释说明）
  config/
    config.yaml         # ★ 该 skill 的全部配置：默认值、参数、开关、inputs 都在这里
    # 需要区分「通用默认 / 本机覆盖」时再拆：default.yaml（分发用，零身份零密钥零本机路径）
    # + local.yaml（后加载，覆盖 default）+ inputs.yaml（输入定义单独放）。同样的键别写两遍。
  src/<pkg>/            # 服务本体（python 包；纯脚本型 skill 可省）
  actions/              # 对服务/平台的成套操作，见 §3
    README.md           # ★ 动作目录：逐个列出动作名 + 一句话说明（当索引用）
    _hook.py            #   共用：找端口 / 读 token / 发请求 / 统一错误（有服务时）
    <动作名>/<动作名>.py
  tests/                # 回归测试（边界样例 + 批量样例，见 §5）
```

**三条硬约束**

1. **配置进 `config/` 下的 yaml，脚本里不写变量**——端口、路径、白名单、开关、模型名、超时，一律从配置读；
   默认值和参数都在配置里，脚本只负责取用。要换环境＝改配置，不改代码。
2. **数据落 `skill_data/<name>/`**（pid / port / jsonl / 日志 / 缓存），**skill 目录里不放运行时数据**。
3. **密钥落 `.secrets/`**（或以环境变量注入），**配置文件里不出现密钥**；对外分发时配置文件用占位符。

> 分发口径：整目录拷走即可用——通用默认在 `default.yaml`（零身份、零密钥、零本机路径），别人只需写自己的 `local.yaml` 与密钥。文档里不写死任何人的身份、账号、路径。

## 2. 输入层（先做这个）

**任何持续接收数据的 skill，第一件事是把「输入」讲清楚**，而不是先写功能。
输入层＝「这个 skill 会遇到哪些进来的东西，每一种该怎么办」。

### 2.1 枚举输入事件，逐个定义

先列出所有可能进来事件，再对每一条回答：**谁触发、内容是什么、要不要叫醒 agent、走哪条通道、多久内不重复**。

定义写进 `config.yaml` 的 `inputs:` 段（配置拆开时放 `config/inputs.yaml`）（**配置化，不写死在代码里**）：

```yaml
inputs:
  - id: agent_done          # 唯一名，代码按 id 找
    desc: 子 agent 完成一轮（无工具调用）
    source: event           # http | event | schedule（见下表）
    wakeup: true            # 要不要唤醒 agent
    channel: notice         # notice | messages | none
    prompt: |               # 唤醒时注入的文本（模板变量用 {name} 这种）
      [subagent] {name} 完成了任务：{summary}
    dedup_s: 60             # 同 id 多久内不重复唤醒（防刷）
```

| source | 是什么 | 是否阻塞 |
|---|---|---|
| `http` | 外部发来的同步请求（要回响应） | 是 |
| `event` | 服务内部产生的异步事件 | 否 |
| `schedule` | 定时自检（每 N 分钟探一次状态） | 否 |

### 2.2 `notice` 与 `messages` 的区别（选错会污染判断）

- **`notice`** —— 系统事件、工具结果、状态告警。**自建服务的默认选择**：进 notice 表，agent 下次醒来在通知里看到，
  不污染任何会话，也不参与「谁在跟我说话」的判断。
- **`messages`** —— 进消息库、参与会话与未读判断。**只有「真的像某个人发来的话」才用**（如平台账号收到私信、
  群里的 @）。自己服务内部产生的事件**不该走这张表**。
- **`none`** —— 只落日志、不唤醒（高频事件，或只在 `status` 里查得到的）。

判定口诀：**这条东西 agent 需不需要主动知道？** 不需要 → `none`；需要但不必马上回话 → `notice`；
需要当成对话内容处理 → `messages`。`wakeup: false` 与 `channel: none` 等价，别两个都写还自相矛盾。

## 3. 动作层（actions/）

- 一个目录一个动作：`actions/<动作名>/<动作名>.py`，**一个动作只做一件事**，用法写在脚本首部 docstring；
- 每个动作要能 **`--dry-run` 空跑**；高风险动作（删数据、改配置、发外网）默认关，开关放配置（本机侧 `local.yaml`）；
- `actions/README.md` 逐个列出「动作名 + 一句话用途」，当索引用（人查、agent 查都靠它）；
- 有服务时：动作一律走 **HTTP** 调服务（`_hook.py` 统一找端口与 token），业务逻辑留在服务里，actions 只做薄封装；
- 没有服务的纯脚本 skill 也一样：一个动作一个脚本，配置从 `config.yaml` 读。

## 4. 开发流程（照顺序走，别跳）

1. **先搭脚手架**：搭出「最小可验证结构」——一个能起（或能跑）的空壳 ＋ 一个最小入口 ＋ 一个动作脚本，
   然后**真跑一次**：调用动作 → 看返回 → 确认输入按预期进来（通道对不对、唤不唤醒对、
   `notice`/`messages` 落对表）。脚手架的唯一用途是**尽早暴露结构问题**，不是功能实现。
2. **逐个输入闭环**（主体工作）：

   ```
   定义 input1 → 写/调 action 测 input1 → 调用验证 → 与预期一致
        ↓（一致才继续）
   定义 input2 → 写/调 action 测 input2 → 调用验证 → 与预期一致
        ↓
   …… 直到所有输入都闭环
   ```

   **不一致就停下来查**（是定义错了、通道选错了、还是服务没接上），不许带着「先凑合」往下做。
3. **补齐剩余动作**：所有输入闭环后，逐一核对「有没有输入之外还需要的能力」——把没被覆盖的动作写完并测试。
4. **清理**：删掉实际运行用不到临时动作/调试代码；检查最小入口**是不是过小**（只剩一行、没有真实逻辑）
   ——过小就改成正常入口（该有的启动、配置加载、输入分派都要在）。
5. **文档收尾**：`SKILL.md` 写清触发条件，`README.md` 写清怎么起/怎么调/有哪些动作，`actions/README.md` 列全动作。

> 原则（老规矩）：**禁止假测试**——不许 dry run 走形式、不许「跑通一个用例就算完」；
> 每步新功能都要真调用、看真返回（边界样例 + 批量样例，见 §5）。

---

## 5. 与 core 的接口（不变）

| 方向 | 接口 |
|---|---|
| 入站（唤醒 agent） | `POST http://host.docker.internal:18086/api/notice`（事件类）或 `/api/messages`（对话类），带 `X-Api-Token` |
| 出站（agent 操作它） | agent 调该 skill 自持的 HTTP 端点（由 `actions/` 脚本封装） |

密钥/令牌一律从 `.secrets/` 读，不硬编码、不进配置明文。

---

## 6. 测试要求

- **边界/攻击性样例**：空输入、超限、重复事件、非法参数各至少一条；
- **批量样例**：主要功能要有成批样例（算法类至少几百组），一次通过不算验证；
- 测试脚本放 `tests/`，能一条命令跑完。
